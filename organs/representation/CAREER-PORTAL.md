# Career and Network Portal

This is the career organism's doorway inside Limen. Limen is the host surface;
it does not replace the engines, ledgers, provider interfaces, or public proof
that already own the work.

## The composed organism

```text
corpvs + portfolio ──identity/evidence──▶ application-pipeline
UMA ──inbound mail + delivery receipts──▶ application-pipeline
Limen/representation ──owner view + gates──▶ application-pipeline
application-pipeline ──staged content──▶ Kerygma/distribution
application-pipeline ──approved action──▶ ATS, email, and browser surfaces

provider receipts ──▶ application-pipeline ──▶ UMA + Limen
relationship outcomes ──▶ Koinonia
person/org/product/repo links ──▶ BIFRONS + SPECVLVM
upstream contribution outcomes ──▶ corpvs/backflow + application-pipeline
```

The machine-readable version is [`career-portal.yaml`](career-portal.yaml).
Operational application and contact state remains private in
`organvm/application-pipeline`; mail state remains with UMA; public identity
remains with the portfolio; contribution state remains with BIFRONS, SPECVLVM,
and the `contrib--*` owners.

## One opportunity, two simultaneous faces

Every live relationship expands in both directions:

1. person → organization → current roles → application eligibility;
2. organization → products → public repositories → maintainers → contribution
   candidates → evidenced learning routed back into the relevant internal repo.

The second face is not a requirement to open a pull request before every
application. It is a research and reciprocity obligation: find the real public
work, avoid collisions, contribute only genuine value, and retain the learning
even when an upstream change is not sent or merged. BIFRONS maps the external
repo; SPECVLVM owns the contribution lifecycle; the application pipeline owns
the career receipt.

The full estate is processed as a recurring coverage ledger. A single operating
day prioritizes live inbound relationships and eligible roles; it never pretends
that hundreds of internal repositories were exhaustively mirrored in one pass.

## Irreversible boundaries

- Jobs must be `us-remote` or `remote-global`; state-restricted roles must
  include the candidate's state. Hybrid, on-site, relocation, and routine travel
  requirements fail closed.
- Submission requires a current staged record, fit score at least 9.0, no more
  than two applications in the rolling seven-day window, one active/submitted
  record per normalized organization, and unchanged URL, résumé, cover letter,
  and answers.
- Mail sends require an exact preview, a current signed authorization receipt,
  a one-shot attempt ID, and provider Sent proof.
- Browser submissions, LinkedIn messages/posts/comments, upstream pull requests,
  credential use, paid services, and destructive actions retain their existing
  action-time gates.
- Kerygma has no LinkedIn API adapter. LinkedIn is an authenticated browser
  surface with confirmation, never an implied automation capability.

## Fixed-point acceptance

- Each live inbound thread has an owner, next state, and provider receipt.
- Each application represented as submitted has an external confirmation and a
  matching pipeline transition.
- Each live network opportunity has a recorded role scan and an outward
  product/repository scan, even when both produce an explicit ineligible or
  no-collision result.
- A second opportunity sync and network ingest are no-ops.
- BIFRONS can map against the hydrated canonical registry; SPECVLVM remains the
  contribution ledger rather than a parallel career-only mirror.
- No result exists only in a local checkout.
